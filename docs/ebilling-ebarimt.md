## 2. Төрийн банкны И-Биллинг

СӨХ-ийн хураамжийг И-Биллингээр цуглуулах нь банкны албан ёсны хэрэглээний
жагсаалтад байгаа (кабель, интернэт, **СӨХ**, цахилгаан, контор, гар утас).

Банк руу холбогдох **2 өөр суваг** байна. Хоёулаа адилхан биш:

### 2.1 Биллер портал — `e.statebank.mn/ebillingnew`

- Нэхэмжлэгч байгууллага (СӨХ) энд бүртгүүлж, сар бүрийн нэхэмжлэхээ оруулна.
- Оршин суугч гялсбанк / ATM / салбар / интернэт банкаар "хэрэглэгчийн код"-оороо
  төлнө.
- **Шинэчилсэн хувилбар үнэгүй.** Мөн өмнө нь зөвхөн Төрийн банкны харилцагч
  төлдөг байсныг өргөтгөж, одоо **аль ч банкны карт, QPay, QR** ажиллана.
  (statebank.mn-ийн бүтээгдэхүүний хуудсан дээрх "100₮ шимтгэл" нь хуучин
  хувилбарын мэдээлэл — 2026-08-27-нд мэдээллүүдээр шалгаж залруулав.)
- Автомат суутгал (харилцах/картын данснаас) тохируулах боломжтой — **энэ нь
  цуглалтын хувийг хамгийн ихээр өсгөдөг хэсэг**.
- ⚠️ **Олон СӨХ энэ үйлчилгээг аль хэдийн авсан байдаг.** Шинэ СӨХ бүрд гэрээ
  байгуулах гэж оролдохоос өмнө даргаас нь асуу — ашиглаж байгаа бол зөвхөн
  файлаа авахад л хангалттай. Дэлгэрэнгүй:
  `docs/onboarding/ebilling-bank-request.md`
- Мэдээлэл солилцоо нь **файл** (Excel/CSV) — API биш.
- **Хотолд одоо байгаа `admin/e-billing` хуудас яг үүнд зориулагдсан.**
  Дутуу зүйл: банкны яг тэр загварыг нь мэдэхгүй байгаа. Загварыг нь авмагц
  экспортын баганыг тааруулна.
- Бүртгүүлэх: `e.statebank.mn/ebillingnew/Sign.aspx`, эсвэл салбараар.
  Утас 1800-1881, contact@statebank.mn.

### 2.2 Корпорэйт гэйтвэй — REST API

- Байгууллагын систем (ERP) банктай **шууд REST/JSON, OAuth**-оор холбогдож,
  дансны хуулгаа автоматаар татдаг. Төрийн банк энэ бүтээгдэхүүнтэй
  (statebank.mn/corporate/product/10127).
- Үнэ нь **хуулга татах давтамжаас** хамаарч ялгаатай.
- Хүсэлтийг албан бичгээр гаргаж, хамтын ажиллагааны гэрээ байгуулна.
- Ач холбогдол: Excel импортын алхам бүрэн алга болно. Айл төлмөгц 10-30 минутын
  дотор өр нь хасагдаж, дарга нар шууд харна.

**Санал:** 2.1-ээр эхэл (гэрээ хялбар, өнөөдөр бэлэн код байна), 2-3 СӨХ дээр
тогтвортой ажилламагц 2.2-ыг ярина.

## 3. е-Баримт (PosAPI 3.0) — ХАМГИЙН ЧУХАЛ ОЛОЛТ

### 3.1 Одоогийн код ажиллахгүй

`app/lib/ebarimt.ts` нь `https://api.ebarimt.mn/api/invoice` руу OAuth
`client_credentials`-ээр POST хийдэг. **Ийм cloud endpoint байхгүй.**
`api.ebarimt.mn` нь зөвхөн лавлах сервис (ТТД шалгах гэх мэт).

PosAPI 3.0 бол **өөрөө байрлуулдаг (self-hosted) service application**:

- `posapi.ini`-д `webServiceHost` / `webServicePort` (**default 7080**) тохируулна
- өөрийн DB хэрэгтэй (SQLite / MySQL / PostgreSQL / MSSQL)
- баримт илгээх: `POST http://{baseUrl}/rest/receipt` — **нэвтрэлтийн header байхгүй**
- буцаах: `DELETE http://{baseUrl}/rest/receipt`
- нэгдсэн систем рүү илгээх: `GET /rest/send`
- төлөв: `GET /rest/info`
- банкны данс: `GET /rest/bankAccounts?tin={TIN}`

Payload-ын бүтэц ч зөрж байна. Одоогийн код `stocks`, `type: '1'/'3'`,
`payments.code: 'P0001'`, `status: 'paid'`, `reportMonth: 'YYYYMM'` гэж илгээдэг.
Бодит 3.0-д:

| Талбар | Зөв утга |
|---|---|
| `type` | `B2C_RECEIPT` / `B2B_RECEIPT` / `B2C_INVOICE` / `B2B_INVOICE` |
| бүтэц | `receipts[].items[]` (2 давхар), `stocks` биш |
| `taxType` | `VAT_ABLE` / `VAT_FREE` / `VAT_ZERO` / `NO_VAT` |
| `payments[].code` | `CASH` / `PAYMENT_CARD` |
| `payments[].status` | `PAID` / `PAY` / `REVERSED` / `ERROR` |
| `reportMonth` | `yyyy-MM-dd` |
| `consumerNo` | иргэний ebarimt дугаар (8 орон) — байвал "хялбар бүртгэл" |

⚠️ **Vercel дээрх Next.js нь localhost:7080 руу хандаж чадахгүй.** PosAPI-г
тусдаа сервер/VPS дээр байрлуулж, хаалттай сүлжээгээр Хотолын API-тай холбоно.

### 3.2 Хотолд яг тохирсон зүйл: PosAPI 3.0 нь олон мерчант дэмждэг

2.0 хувилбар нэг л ААН-ийг дэмждэг байсныг **3.0 нь нэг PosAPI дээр олон ААН
бүртгэж, тус бүрийн баримтыг гаргах** боломжтой болгосон. Мөн "түрээслүүлэгч /
түрээслэгч" (багц баримт) шийдэлтэй.

Өөрөөр хэлбэл **Хотол нэг PosAPI ажиллуулаад, СӨХ бүрийг мерчантаар нь бүртгэж,
СӨХ бүрийн нэрээр баримт гаргах боломжтой.** СӨХ бүр тус тусдаа кассын машин
авах, техникч хөлслөх шаардлагагүй — энэ нь Хотолын томоохон давуу тал болно.

### 3.3 Бүртгэлийн урсгал

1. Хотол **"хэрэглэгчийн систем нийлүүлэгч" / оператор** эрхийн хүсэлт гаргана
   (e-invoice.ebarimt.mn → Хүсэлт цэс). Дэмжлэг: posapi@itc.gov.mn
2. PosAPI-г серверт суулгаж, оператор эрхээр нэвтэрч **идэвхжүүлнэ** →
   пос дугаар + сугалааны эрх авна
3. `operator.ebarimt.mn` дээр пос дугаараар хайж, **СӨХ бүрийн ТТД-аар мерчант
   нэмэх хүсэлт** илгээнэ
4. СӨХ өөрийн `e-invoice.ebarimt.mn` → Хүсэлт → PosAPI хүсэлт → Операторын
   холболт хэсгээс **баталгаажуулна**
5. Тэр СӨХ-ийн нэрээр баримт гарч эхэлнэ

### 3.4 НӨАТ

Ихэнх СӨХ НӨАТ суутган төлөгч биш (50 сая доогуур). Тэр тохиолдолд:

- **сугалааны дугаар үүснэ** (оршин суугчид таалагдана — буцаан олголт)
- **НӨАТ бодохгүй** → `totalVAT: 0`
- Одоогийн кодын `Math.round(amount / 11)` нь **буруу**, засах ёстой

СӨХ бүр НӨАТ төлөгч эсэхийг `ebarimt_configs`-т талбар болгон хадгална.

Хууль зүйн тал: борлуулалт/үйлчилгээ үзүүлдэг бүх ААН баримт олгох үүрэгтэй,
НӨАТ төлөгч эсэх нь үүнийг өөрчлөхгүй. Тиймээс СӨХ хураамждаа баримт гаргах нь
зөв. Гэхдээ **энэ бол миний уншсанаас гаргасан дүгнэлт — СӨХ-ийн нягтлан эсвэл
татварын байцаагчаар баталгаажуулах хэрэгтэй.**

## 6. Бодит гэрээг судлав (2026-09-03)

Гринланд-687 СӨХ ↔ Төрийн банкны хооронд байгуулагдсан **«Биллер байгууллагатай
хамтран ажиллах гэрээ»**-ний 7 хуудсыг бүтнээр нь уншив (гэрээ №02, 2026-02-02,
хугацаа 1 жил, авто сунгалттай). Үндэслэл: Төрийн банкны Гүйцэтгэх захирлын
2023-04-12-ны **А/176 тоот тушаал**-аар батлагдсан журмын Хавсралт 1.
Гэрээт нэгж нь тухайн дүүргийн **тооцооны төв** (энэ тохиолдолд СБД).
Хавсралт 1 = «төлбөр хураадаг байрнуудын жагсаалт»: Хот | Дүүрэг | Хороо |
Байр | Корпус | Өрхийн тоо.

Гэрээ нь **СӨХ-ийн нэр дээр** байгуулагддаг, мөнгө **СӨХ-ийн харилцах данс** руу
төвлөрдөг (1.1). Хотол тал биш — энэ нь [[project_bank_qr_payments]]-ийн
«Хотол мөнгө барихгүй» зарчимтай бүрэн нийцнэ.

### 6.1 Хотолд хамгийн чухал 5 олдвор

**1) «Онлайн биллер байгууллага» гэсэн ангилал байна (1.2.12)** — тодорхойлолт нь
«**гуравдагч этгээдээр дамжуулан** Төрийн банкны орлого программд бүртгэлтэй
биллер байгууллага». Энэ бол яг Хотол шиг платформд зориулсан ангилал.
Түүнээс гадна 4.1.1: энгийн биллер сар бүр и-мэйлээр файл илгээдэг бол
**онлайн биллер нь «ойр тутам эсвэл 24/7 горимоор» илгээнэ**. Өөрөөр хэлбэл
сар бүрийн гар ажиллагааны оронд тасралтгүй урсгал зөвшөөрөгддөг.

**2) е-Баримтыг БАНК гаргана (5.2.3)** — «төлсөн харилцагчид НӨАТУС-ээс
олгогдож буй **ДДТД болон сугалааны дугаар бүхий төлбөрийн баримт олгох**» нь
банкны үүрэг. Энэ сувгаар орсон төлбөрт Хотол PosAPI ажиллуулах шаардлагагүй.
→ §3-ын «PosAPI-г VPS дээр суулгах» гэсэн хамгийн том саад **энэ сувгийн
хувьд арилна**. PosAPI нь зөвхөн банкнаас гадуур (бэлэн, QR, шилжүүлэг)
орсон төлбөрт хэрэгтэй болно.

**3) Хэрэглэгчийн кодын формат тодорхой боллоо (1.2.4)** — «Орлого программд
тухайн хэрэглэгчийн **хаягийг илэрхийлэх тоон утга**». Өрнөлт СӨХ-ийн даргын
өгсөн өрийн тайлан яг энэ программаас хэвлэгдсэн бөгөөд хаягийн бичиглэл нь
**`<байр> / <4 оронтой тоот> - <корпус>`** (ж: `9.2 / 0019 - 0`).
→ `residents.bank_customer_code`-ыг ЯГ ЭНЭ форматаар бөглөвөл банкны
жагсаалттай 100% тулна. Санамсаргүй «9B34» гэх мэт өөрийн код зохиох хэрэггүй.

**4) Автомат суутгал гэрээгээр баталгаажсан (5.2.5)** — «гэрээт нэгж нь СӨХ-ны
хүсэлтийг үндэслэн **сар бүр тогтмол дүнгээр таталт хийж** орлого программд
нэхэмжлэхийг оруулах». Цуглалтын хувийг хамгийн ихээр өсгөдөг хэсэг.

**5) Төлөгдөөгүй айлын жагсаалт нь гэрээний ҮҮРЭГ (6.2.19)** — биллер нь
«Гялсбанк үйлчилгээнд бүртгүүлж, **сар бүр төлбөр төлөгдөөгүй айлуудын
жагсаалтыг татаж авч, тулган баталгаажуулсан байх**». Энэ жагсаалт нь
`app/admin/e-billing` хуудасны импорт руу шууд ордог файл. Дарга ямар ч
байсан татах үүрэгтэй тул нэмэлт ачаалал үүсэхгүй.

### 6.4 Дутуу байгаа зүйлс (банкнаас авах)

1. **Хавсралт 2 — «Банкны стандарт файлын загвар»** (нэхэмжлэлийн файл).
   Энэ бол хамгийн чухал дутуу баримт: үүнгүйгээр `admin/e-billing`-ийн
   экспортыг банкны загварт тааруулж чадахгүй.
2. **Хасалтын файлын стандарт загвар** (4.1.5.2).
3. **Хавсралт 3** — үлдэгдлийн тулгалтын акт загвар.
4. **А/176 журмын бүрэн эх** — ялангуяа «онлайн биллер»-ийн бүртгэлийн журам
   (2.1.26 нь и-мэйл хаягийг тодорхойлдог).
5. **Гол асуулт:** онлайн биллерийн 24/7 суваг нь и-мэйл автоматжуулалт уу,
   эсвэл жинхэнэ API юу? Хариу нь Хотолын архитектурыг шийднэ.

### 6.5 Санал болгох зам

**Алхам 0 (өнөөдөр, зардалгүй):** `bank_customer_code`-ыг банкны хаягийн
форматаар бөглөх. Гэрээ, банктай харилцах шаардлагагүй, гэхдээ 7.1-ийн
эрсдэлийг арилгаж, импортын тулгалтыг 100% болгоно.

**Алхам 1 (1-2 долоо хоног):** Гринланд-687 дээр **пилот** — гэрээ нь аль
хэдийн хүчинтэй, шинээр байгуулах шаардлагагүй. Даргаас Хавсралт 2-ын
загварыг авч, `admin/e-billing`-ийн экспортыг тааруулах. Дараа нь Гялсбанкнаас
төлөгдөөгүй жагсаалтыг татаж импортлон, бүтэн нэг мөчлөг ажиллуулж үзэх.
⚠️ Өрнөлт СӨХ ч гэсэн энэ системд аль хэдийн байгаа бололтой — даргын өгсөн
өрийн тайлан банкны Орлого программаас хэвлэгдсэн. Түүнээс лавлах.

**Алхам 2:** ажиллаж байгааг батласны дараа Төрийн банкнаас **«онлайн биллер»**
статус хүсэх. Хотол нэг холболтоор бүх СӨХ-ийн нэхэмжлэхийг тасралтгүй
илгээнэ. Энэ үед л 5.1.6-ийн uptime, 6.2.18-ийн зөвшөөрлийн үүрэг Хотолд ирнэ.

**Алхам 3:** е-баримт — §3-ын PosAPI төслийг **банкнаас гадуурх** төлбөрт л
хэрэгтэй гэж хумих. Банкны сувгаар орсон төлбөрт банк өөрөө баримт гаргана (5.2.3).

**Хэзээ ч бүү мартагдуул:** банкны суваг нь **бүтэн дүнгээр л** ажиллана.
Хэсэгчилсэн төлөлт, өр барагдуулах гэрээ, өрийн хуваарь бүгд банкны QR /
шилжүүлгийн сувгаар үлдэнэ. Хоёр суваг зэрэг ажиллана.
