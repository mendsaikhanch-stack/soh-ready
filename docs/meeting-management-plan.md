# Хурлын удирдлагын модуль (Meeting Management): судалгаа, төлөвлөгөө

> Огноо: 2026-10-15 · Төлөв: **1-р шат кодоор хэрэгжсэн (2026-10-15), миграц гараар ажиллуулах хүлээгдэж байна** — §13.
> Энд «байгаа» гэж бичсэн бүхнийг кодоос шалгаж, `файл:мөр`-ээр иш татсан.
> Шалгаагүй зүйлийг **(шалгаагүй)** гэж тэмдэглэсэн.

---

## 0. Товч дүгнэлт

- Репод **хурал гэсэн ойлголт огт байхгүй.** Хурлын хүснэгт, API, хуудас, ирц, итгэмжлэл,
  хурлын тэмдэглэлийн архив аль нь ч алга.
- Санал хураалтын хоёр систем байгаа ч аль нь ч бүх гишүүдийн хурлыг орлохгүй:
  - **Цахим ТУЗ** (`proposals`) нь зөвхөн ТУЗ-ийн гишүүдэд (≤50 утас) зориулагдсан.
  - **Санал асуулга** (`polls`) нь нэргүй тийм/үгүй тоолуур. Давхар саналаас зөвхөн
    хөтчийн localStorage хамгаалдаг.
- Хурлын модулийг **тусдаа шинэ хүснэгт, шинэ API**-гаар нэмэх нь зөв. Байгаа модулиудыг
  засах шаардлагагүй.
- Хуулийн тоон шаардлагыг (зар хүргэх хугацаа, ирцийн хувь, шийдвэрийн босго) хуулийн
  эх бичвэрээс **хараахан тулгаагүй**. Тиймээс кодонд хатуу бичихгүй, хурал бүрд
  тохиргоо болгож хадгална (§9).

### 1.2 Нэвтрэлт

- **Оршин суугч** Supabase Auth ашиглана:
  - Нэвтрэх: `${phone}@toot.app` + нууц үг (`app/(mobile)/login/page.tsx:55-60`).
  - API: `Authorization: Bearer` токеныг `auth.getUser()`-ээр шалгана (жишээ нь `app/api/residents/profile/route.ts:50-59`).
  - ⚠️ Клиент профайлаа `auth_user_id`-аар биш, **утасны дугаараар** ачаалдаг (`app/lib/auth-context.tsx:75-81`).
- **Дарга (admin), супер админ, ОСНАА, байцаагч** өөрийн HMAC cookie ашиглана:
  - Токен: `timestamp:sokhId:userId:role:nonce[:demo].sig` (`app/lib/session-token.ts:15-27`).
  - Шалгалт: `checkAuth` / `checkAnyAuth` (`session-token.ts:94-118`).
  - Эрхүүд: `admin | superadmin | osnaa | inspector` (`session-token.ts:75`). **Нарийн бичиг,
    ТУЗ-ийн гишүүн, нягтлан гэсэн эрх байхгүй.**
- `middleware.ts` гарын үсэг шалгадаггүй (`:9-22, 103-117`). Хамгаалалтыг маршрут бүр
  өөрөө хийдэг.

### 1.3 Tenant (СӨХ) тусгаарлалт

- Tenant түлхүүр: `sokh_id BIGINT → sokh_organizations(id)` (`supabase-v2.sql:2`).
- Proxy select/update/delete-д `eq.sokh_id`-г **албадан** нэмдэг. Insert-д `sokh_id`-г
  сессийнхээр дарж бичдэг (`app/api/admin/db/route.ts:163-193`).
- RLS:
  - `current_user_sokh_ids()` (`supabase-tenant-scope-migration.sql:52-65`) ба зарим хүснэгтийн tenant SELECT бодлого.
  - Аль SQL файл production-д бодитоор ажилласныг энэ судалгаагаар **шалгаагүй**.
    Memory-ийн мэдээллээр 2026-08-29-ний аудитад «RLS prod-д ажиллаагүй» гэж бичигдсэн.
- Илэрсэн цоорхой (хурлын модульд шууд хамаатай):
  1. Нэвтэрсэн оршин суугч өөрийн СӨХ-ийн **бүх** оршин суугчийн мөрийг (утас, өр) уншиж
     чадна (`supabase-tenant-scope-migration.sql:82-84`). Иймд хурлын өгөгдлийг anon
     client-ээр бүү нээ.
  2. `/api/push/send` даргын сессийн `sokh_id`-г **хүчлэхгүй**. Биеэс нь ирсэн `sokh_id`-г
     ашигладаг, хоосон бол бүх захиалагч руу илгээнэ (`app/api/push/send/route.ts:38-42`).
     Хурлын урилгыг энэ замаар бүү явуул (§8).

## 2. Хурлын холбоотой одоо байгаа функц

### 2.1 Цахим ТУЗ: `proposals` (`supabase-board-voting-migration.sql`)

- Санал өгөгч нь даргын гараар оруулсан **утасны дугаарууд** (≤50, `app/api/vote/create/route.ts:14`).
  `residents`, сууцтай холбоогүй.
- Саналыг утасны дугаараар тоолно: нэг утас нэг санал, `UNIQUE(proposal_id, phone_number)`.
- Баталгаажуулалт: SMS OTP (`app/api/vote/otp/route.ts`). **SMS stub тул бодитоор очдоггүй.**
- Шийдвэр: `зөвшөөрсөн / нийт урьсан × 100 ≥ босго` (`app/lib/board-server.ts:114-115`).
  Тусдаа ирц гэсэн ойлголт байхгүй. `auto_approve_on_timeout` асаалттай бол санал
  өгөөгүй хүнийг «зөвшөөрсөн» гэж автоматаар бичнэ (`:59-91`).
  **Энэ логикийг гишүүдийн хуралд хэрэглэх ёсгүй** (шаардлага 7-той зөрчилдөнө).
- Протокол: хэвлэх хуудас «ЦАХИМ ТУЗ-ИЙН ХУРЛЫН ПРОТОКОЛ» (`app/vote/[id]/result/page.tsx:98-168`).
  Хадгалагддаггүй.
- `/api/vote/*` маршрутууд `audit_logs` бичдэггүй.

### 2.2 Санал асуулга: `polls` (`supabase-v2.sql:25-36`)

- `/admin/polls` (цэсэнд байгаа) болон `/admin/polling` (цэсэнд холбоосгүй) хоёулаа
  ижил хүснэгт ашигладаг.
- Оршин суугч `yes_count`/`no_count`-ийг клиентээс шууд нэмдэг
  (`app/(mobile)/sokh/[id]/voting/page.tsx:76-83`). Давхар саналаас зөвхөн localStorage хамгаална (`:45, 88`).
- `poll_votes` хүснэгт байгаа ч ашиглагддаггүй.
- `docs/fb-posts/carousel-02-hurlyn-irts.md:7-12` өөрөө «polls нь ирц баримтжуулдаггүй» гэж бичсэн.

### 2.3 Бусад

- `app/admin/booking` дахь «Хурлын өрөө» нь өрөө захиалга, хуралтай холбоогүй.
- Зөвлөгөөний `meeting-*` болон `voting-*` картууд хуулийн 7, 8, 9, 10, 13-р зүйлийг дурддаг
  (`app/lib/advice/data.ts:986-1080`).
  ⚠️ `meeting-convene` карт «Зарлал цэсээр илгээхэд хэн хэзээ уншсан бүртгэл үлддэг»
  гэж бичсэн. **Ийм бүртгэл кодонд байхгүй.** Хурлын модуль гарах хүртэл энэ өгүүлбэрийг
  засах шаардлагатай.

### 2.4 Хамрах хүрээний матриц

| Шаардлага | Цахим ТУЗ | Санал асуулга | Зарлал |
|---|---|---|---|
| Урилга + хүргүүлсэн огноо | Хэсэгчлэн (`invited_at`, SMS stub) | Үгүй | Хэсэгчлэн (`created_at`, хүргэлтийн лог байхгүй) |
| Ирц | Үгүй | Үгүй | Үгүй |
| Итгэмжлэл | Үгүй | Үгүй | Үгүй |
| Урьдчилсан санал | Хугацаат цахим санал байдлаар | Нэргүй | Үгүй |
| Ирцтэй санал хураалт | Ирц биш, босго | Үгүй | Үгүй |
| Хурлын тэмдэглэл | Хэвлэдэг, хадгалдаггүй | Үгүй | Үгүй |
| Шийдвэрийн архив | `status` / `finalized_at` | Хаагдсан асуулга | Үгүй |

**Дүгнэлт:** 7 шаардлагаас бүрэн хэрэгжсэн нь **0.** Хэсэгчилсэн хэрэгжилтүүд нь өөр
зорилгоор хийгдсэн тул дахин ашиглахгүй, зөвхөн загвар болгон ашиглана.

## 3. Дутагдаж буй функц

1. Хурлын бүртгэл: төрөл (ээлжит/ээлжит бус), огноо, газар/цахим холбоос, зарлан
   хуралдуулагч, төлөв.
2. Хэлэлцэх асуудал (agenda) ба асуудал бүрийн шийдвэрийн төсөл.
3. **Санал өгөх эрхтэй нэгжийн хөлдөөсөн жагсаалт.** Хурал зарласан мөчийн хуулбар байна,
   дараа нь оршин суугчийн бүртгэл өөрчлөгдсөн ч хурлын тооцоо хөдлөхгүй.
4. Зар хүргэлтийн бүртгэл: нэгж бүр, суваг бүрээр «илгээсэн», «хүргэгдсэн», «нээж уншсан»,
   «гараар гардуулсан» гэсэн төлвүүдийг тус тусад нь.
5. Ирцийн бүртгэл: биечлэн, цахимаар, итгэмжлэлээр. Хэн, хэзээ бүртгэснийг хадгална.
6. Итгэмжлэл: итгэмжлэгч сууц, итгэмжлэгдэгч, баримтын файл, хүчинтэй хугацаа, хамрах
   асуудал, баталгаажуулсан хүн, цуцлалт.
7. Урьдчилсан санал (хурлаас өмнө, цахимаар) ба хурал дээрх санал. **Хоёрыг тусад нь**
   хадгалж, давхардлын дүрэмтэй байна.
8. Ирц ба санал хураалтын дүнг тооцоолох. Ирц бүрдээгүй бол хүчин төгөлдөр гэж автоматаар
   тэмдэглэхгүй.
9. Хурлын тэмдэглэл: хувилбар, PDF, гарын үсэгтэй скан, батлагдсан огноо.
10. Шийдвэрийн архив: дугаар, текст, хүчин төгөлдөр болсон огноо. Оршин суугчид харагдана.
11. Хурлын бүх үйлдлийн устгагдахгүй аудит лог.
12. Бодит хүргэлтийн суваг: SMS провайдер залгах (тусдаа ажил) ба оршин суугчтай
    холбогдсон push.

## 4. Санал болгож буй өгөгдлийн загвар

> Энэ бол **загвар**, миграцын файл биш. Хэрэгжүүлэх үед
> `supabase-meetings-migration.sql` болгон гаргаж, SQL Editor-т гараар ажиллуулна.

### 4.1 Үндсэн зарчим

- Хүснэгт бүр `sokh_id BIGINT NOT NULL REFERENCES sokh_organizations(id)` агуулна.
- **RLS = бүгдийг хаах** (`audit_logs`, `admin_users`-тэй адил): `anon` ба `authenticated`-д
  эрх өгөхгүй. Бүх унших, бичих үйлдэл зөвхөн тусгай API маршрутаар service role-оор
  явна. Ингэснээр production-ийн RLS төлөв ямар ч байсан хурлын өгөгдөл задрахгүй.
- Хуулийн ач холбогдолтой мөрийг (хүргэлт, ирц, санал, итгэмжлэл) **UPDATE/DELETE хийхгүй.**
  Засах бол шинэ мөр нэмж, хуучныг `superseded_by`/`revoked_at`-аар хүчингүй болгоно.
  Үүнийг trigger-ээр хамгаална.

```text
  cast_by ('owner'|'proxy'|'admin_paper_entry'), proxy_id, auth_user_id,
  cast_at, ip, user_agent, superseded_by, created_at
  -- (agenda_item_id, eligible_unit_id)-д нэг л идэвхтэй санал

meeting_results                 -- тооцоолсон дүн, хүний баталгаажуулалт тусдаа
  id, meeting_id, sokh_id, agenda_item_id (null = хурлын ирцийн дүн),
  eligible_count, eligible_weight, present_count, present_weight,
  for_weight, against_weight, abstain_weight, prevote_weight, in_meeting_weight,
  quorum_status ('not_met'|'met'), outcome ('passed'|'rejected'|'no_quorum'),
  computed_at, computed_by ('system'),
  confirmed_by_admin_id, confirmed_at        -- хүн батлах хүртэл хүчин төгөлдөр бус

meeting_minutes
  id, meeting_id, sokh_id, version, body_md, pdf_path, signed_scan_path,
  chair_name, secretary_name, approved_at, created_by_admin_id, created_at

meeting_decisions               -- архив, оршин суугчид харагдана
  id, meeting_id, sokh_id, agenda_item_id, decision_no, text,
  outcome, effective_from, published_at, created_at

meeting_events                  -- зөвхөн нэмэх аудит лог
  id, meeting_id, sokh_id, actor_type ('admin'|'resident'|'system'),
  actor_id, action, payload JSONB, ip, user_agent, created_at
  -- UPDATE/DELETE-ийг trigger-ээр хориглоно
```

## 6. Интерфейс

### 6.1 Даргын самбар: `/admin/meetings`

1. **Жагсаалт:** төлөв бүрээр шүүнэ.
2. **Шинэ хурал (шидтэн):** үндсэн мэдээлэл → хэлэлцэх асуудал → дүрэм (ирц %, саналын
   жин, урьдчилсан санал) → «Хурал зарлах».
3. **Зар хүргэлт:** нэгж бүрийн төлөвийн хүснэгт (илгээсэн, нээсэн, гараар гардуулсан,
   хүрээгүй). Хүрээгүй нэгжүүдийг тусад нь харуулна.
4. **Итгэмжлэл:** ирсэн баримтыг харж батлах эсвэл татгалзах.
5. **Хурлын өдөр:** ирц бүртгэх (жагсаалтаас сонгох, QR). Ирцийн самбар «X / Y нэгж,
   жингийн Z%, шаардлага N%».
6. **Санал:** асуудал бүрээр урьдчилсан санал болон хурлын саналыг тусад нь харуулж,
   нийлбэрийг гаргана.
7. **Дүн ба батлалт:** «Ирц бүрдээгүй» бол батлах товч идэвхгүй, улаан мэдэгдэлтэй.
8. **Тэмдэглэл ба архив:** загвараас тэмдэглэл үүсгэх, PDF, гарын үсэгтэй скан байршуулах.

Нэр томъёо энгийн монголоор: «Хурал зарлах», «Ирц», «Итгэмжлэл», «Урьдчилсан санал».
Draft, quorum, proxy гэх мэт үг UI-д гарахгүй.

### 6.2 Оршин суугчийн апп: `/sokh/[id]/meetings`

- **Ирэх хурал:** огноо, газар, хэлэлцэх асуудал, хавсралт.
- **«Урьдчилсан санал өгөх»:** зөвхөн өмчлөгч, эрхтэй нэгж л харна. Түрээслэгчид
  «Өмчлөгчийн итгэмжлэлээр оролцоно» гэсэн тайлбар гарна.
- **«Итгэмжлэл өгөх»:** итгэмжлэгдэгчийн нэр, утас, баримтын зураг.
- **Өнгөрсөн хурлууд:** шийдвэр, батлагдсан тэмдэглэлийн PDF.

## 8. Зар хүргэлтийн бодит байдал

Хуулийн нотолгоонд «илгээсэн» ба «хүрсэн»-ийг ялгах ёстой. Одоогийн байдлаар:

- **SMS stub** тул `sent`/`delivered` гэж **бичихгүй.** Провайдер залгах хүртэл SMS сувгийг
  UI-д «идэвхгүй» гэж харуулна. `sendSms` нь `ok:true` буцаадаг тул түүнд итгэж
  `delivered` гэж бичвэл худал нотолгоо үүснэ.
- **Push** нь оршин суугчтай холбоогүй. Нэгж тус бүрт хүрсэн эсэхийг тогтоох боломжгүй тул
  зөвхөн `app` сувгийн `opened` (оршин суугч хурлын хуудсыг нээсэн) мөрийг бодит
  нотолгоо гэж тооцно.
- **Цаасаар гардуулах** нь ихэнх СӨХ-д гол суваг хэвээр байна. Дарга гарын үсэгтэй
  хуудсын зургийг `proof_file_path`-д хавсаргана.
- Хуудсан дээр «зар хүргэх хугацаа» (`scheduled_at − min_notice_days`) өнгөрсөн мөртлөө
  нэгж бүрд хүрээгүй бол сануулга харуулна. Хурал зарласан огноо ба нэгж бүрийн хүргэсэн
  огноо тусдаа хадгалагдана.

## 9. Хуулийн шаардлага ба хүчин төгөлдөр байдлын дүрэм

**Эх сурвалж:** «Сууц өмчлөгчдийн холбооны эрх зүйн байдал, нийтийн зориулалттай орон сууцны
байшингийн дундын өмчлөлийн эд хөрөнгийн тухай хууль» (2003). Зүйлүүд: 7 (дээд байгууллага),
8 (хурал зарлах), 9 (шийдвэрийн хүчин төгөлдөр байдал), 10 (ТУЗ), 13 (өмчлөгчийн эрх)
(`docs/advice-module.md:68-77`).

**⚠️ Тоон шаардлагыг шалгаагүй.** Зөвлөгөөний картууд «олонх оролцвол хүчинтэй» гэж
ерөнхийлөн бичсэн бөгөөд яг тоог эх бичвэрээс шалга гэж зөвлөсөн (`app/lib/advice/data.ts:1010`).
Иймд дараах зарчмаар хийнэ:

1. Ирцийн %, зар хүргэх хоног, асуудал бүрийн шийдвэрийн босго, урьдчилсан саналыг ирцэд
   тооцох эсэх, саналын жинг **хурал бүрийн тохиргоо** болгоно.
2. Хурал зарлах мөчид эдгээр тохиргоог **хөлдөөнө** (`rules_frozen_at`). Дундуур нь
   өөрчлөхгүй.
3. Хуулиас тулгасны дараа анхдагч утгыг нэг газар (`app/lib/meetings/rules.ts`) хуулийн
   зүйл, заалтын ишлэлтэй бичнэ.

**Хүчин төгөлдөр байдлын дүрэм (шаардлага 7):**

- Систем зөвхөн **тооцоолно** (`meeting_results.quorum_status`). Автоматаар «хүчин
  төгөлдөр» гэж хэзээ ч бичихгүй.
- `quorum_status='not_met'` үед:
  - асуудал бүрийн `outcome = 'no_quorum'`;
  - `confirm` маршрут **409** буцаана;
  - DB түвшинд CHECK/trigger: `confirmed_at IS NOT NULL ⇒ quorum_status = 'met'`.
- Ирц бүрдсэн ч батлах нь даргын **гар үйлдэл** (хэн, хэзээ батласан нь хадгалагдана).
- Цахим ТУЗ-ийн `auto_approve_on_timeout` шиг «санал өгөөгүйг зөвшөөрсөнд тооцох» логик
  энэ модульд **байхгүй.**
- Хурал ирцгүй болбол `closed`, тэмдэглэлд «ирц бүрдээгүй» гэж бичигдэнэ. Дахин хурал
  зарлахад шинэ `meetings` мөр үүснэ.

**Тус тусад нь бүртгэх зүйлс (шаардлага 6):**

| Зүйл | Хүснэгт | Тусдаа хадгалах түлхүүр |
|---|---|---|
| Зар хүргүүлсэн огноо | `meeting_notices` | нэгж × суваг, `sent_at` / `delivered_at` / `opened_at` |
| Ирц | `meeting_attendance` | нэгж, `mode`, `checked_in_at` |
| Итгэмжлэл | `meeting_proxies` | итгэмжлэгч нэгж, баримт, баталгаажуулалт |
| Урьдчилсан санал | `meeting_ballots` (`phase='prevote'`) | — |
| Хурлын санал | `meeting_ballots` (`phase='in_meeting'`) | — |
| Дүн | `meeting_results` | тооцоолсон ба баталсан тусдаа |

| Даргын UI | `/admin/meetings` (жагсаалт + шинэ хурал), `/admin/meetings/[id]` (засах, зарлах, сууцны жагсаалт, цуцлах, түүх); цэсэнд «Гишүүдийн хурал» |

Шийдвэрүүд:
- §12-ын асуултуудыг (саналын жин, ирцийн %, зар хүргэх хоног, урьдчилсан санал ирцэд тооцох эсэх) **хурал бүрд дарга сонгоно** — систем анхдагч утга тавихгүй, бөглөөгүй бол зарлахгүй.
- Сууц = `residents`-ийн (байр, тоот) нормчилсон хос (латин/кирилл ижил үсгийг нэгтгэнэ). `pending_claim` мөрийг тооцохгүй. Эзэн (`owner`) мөр байвал түүнийг, үгүй бол эхний мөрийг авч «Өмчлөгч тодорхойгүй» гэж тэмдэглэнэ; олон эзэнтэй бол «Олон өмчлөгчтэй». Production-д `resident_type` ихэнхдээ хоосон тул ихэнх сууц «тодорхойгүй» гарна — 3-4-р шатанд дарга тодруулах урсгал хэрэгтэй.
- Зарлах үед `scheduled_at ≥ одоо + min_notice_days` байх ёстой.
- Миграц ажиллаагүй үед API `migrated:false`/503 буцааж, хуудас «идэвхжээгүй» гэж харуулна — бусад хуудсанд нөлөөгүй.

Шалгасан: PGlite (Postgres) дээр миграцыг 2 удаа ажиллуулж, tenant FK, давхар зарлалт, зарласны дараах засвар/устгал, аудит лог засах, ирцгүй дүн батлах, цуцалснаа сэргээх, `per_area` талбайгүй, зар хүргэх хугацаа хүрэхгүй — бүгд хориглогдож буйг; 23A/23А нэгдэж, pending_claim хасагдаж буйг баталгаажуулав. `npm run build` амжилттай.

Хийгээгүй (дараагийн шат): оршин суугчид урилга хүргэх, оршин суугчийн хуудас, итгэмжлэл, ирц, санал, тэмдэглэл; супер админы харах эрх.
