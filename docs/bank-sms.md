# Банкны SMS → автомат гүйлгээ бүртгэл (ХасБанк → ICTown СӨХ)

Төлөв (2026-10-26): **migration + seed production-д ажилласан; deploy, утсан дээрх туршилт хийгдээгүй.**
2026-10-26: `supabase-bank-sms-migration.sql` ажиллав — 4 хүснэгт RLS=true, policy 0,
anon 401, `payments_provider_check`-д `bank_sms` орсон. Seed-ийн 5 дүрэм тус бүр
`owner_rows = 1`; seed ажиллаж 5 дүрэм орсон, normalized_pattern нь `normalizeReference`-тэй таарна.

Төхөөрөмж, SIM-ийн тодорхой мэдээлэл: `docs/bank-sms-ictown.local.md` (git-д орохгүй).

## Урсгал

```
ХасБанк (илгээгч 131888) ──SMS──▶ Samsung утас (СӨХ-ийн SIM)
   │  apps/android-sms-bridge: илгээгч шүүх → SQLite дараалал → WorkManager retry
   ▼  HTTPS, Authorization: Bearer khsms_…
POST /api/bank-sms ── токен (SHA-256) шалгах, rate limit, 16KB хязгаар, validation
   ▼
bank_sms_events        эх SMS (утасны messageId-аар давхардалгүй)
   ▼  parseBankSms — зөвхөн «ORLOGO орлоо» формат; «Uldegdel» = үлдэгдэл
bank_transactions      (sokh, данс, QPay reference)-ээр давхардалгүй
   ▼  payment_reference_mappings — бүтэн утга ЯГ таарах («613тоот» → 2-2-613)
residents (building «2-2», apartment «613», даргын мөр = floor бөглөгдсөн)
   ▼  ганц нээлттэй нэхэмжлэх + дүн яг таарах + auto_apply асаалттай
payments (provider 'bank_sms') + invoices.paid_amount + residents.debt
   — bank_sms_apply_payment() НЭГ DB transaction дотор, мөрийг түгжиж
```

Эргэлзээтэй бүх тохиолдол `needs_review` төлөвт `/admin/bank-sms`-д очно:
дүрэм алга, тоотод олон айл, дүн зөрүүтэй, олон нэхэмжлэх, формат танигдаагүй,
дансны маск таарахгүй, зарлага. Юу ч устгагдахгүй.

## 1. Migration ажиллуулах

Production DB-д **зөвшөөрөл авсны дараа**, Supabase ▸ SQL Editor-т дараалан:

1. `supabase-bank-sms-migration.sql` — бүгдийг сонгоод RUN. Давтан ажиллуулж болно.
   Одоо байгаа өгөгдөлд хүрэх ганц өөрчлөлт: `payments_provider_check`-ийг
   устгаад `bank_sms`-тэй дахин үүсгэнэ (өргөтгөл, мөр өөрчлөхгүй).
2. `supabase-bank-sms-ictown-seed.sql` — RUN. Доод талын ШАЛГАХ query-г
   ажиллуулж, 5 дүрэм тус бүр `owner_rows = 1` байгааг шалгана. 0 эсвэл >1 бол
   тэр тоотын гүйлгээ автоматаар холбогдохгүй (needs_review) — residents-ийг засна.
3. `sql/diagnostics/bank-sms-rls-check.sql` — хүлээгдэж буй үр дүнг файлын
   толгойд бичсэн.

## 6. Аюулгүй байдлын шийдвэрүүд

- **Токен**: 256-бит санамсаргүй, DB-д SHA-256. Утсан дээр Android Keystore
  AES-GCM-ээр шифрлэсэн, backup-д орохгүй. Redirect дагахгүй (токен өөр хост руу
  алдагдахгүй), зөвхөн системийн CA.
- **Сервер утсанд сохроор итгэхгүй**: илгээгчийг дахин шалгана, `receivedAt`
  боломжгүй бол хаяна (серверийн цаг тусдаа), дансны маск таарахгүй бол review.
- **SQL injection**: бүх утга PostgREST параметрээр; SMS текст SQL-д нийлэхгүй.
- **Лог**: SMS-ийн текст console-д бичигдэхгүй, зөвхөн алдааны код.
- **CSRF**: утасны API cookie ашигладаггүй (Bearer). Админ API — `admin-session`
  cookie нь `SameSite=strict` + `application/json` шаардана.
- **Tenant**: 4 хүснэгт RLS-тэй, policy-гүй → anon/authenticated (оршин суугчийн
  апп) юу ч харахгүй. Админ API session-ий `sokh_id`-аар шүүнэ; superadmin `sokhId`
  заавал дамжуулна. RPC нь оршин суугч, нэхэмжлэх тухайн СӨХ-ийнх эсэхийг дахин шалгана.
- **Retention**: эх текст 90 хоног (шийдэгдээгүй review-г хадгална); утсан дээр
  хүргэгдмэгц текст арилна, мета 14 хоногийн дараа устна.
- **Rate limit**: in-memory (одоогийн бусад endpoint-тэй ижил) — Vercel-ийн
  instance бүрт тусдаа тоологдоно.

## 7. Нээлттэй асуудал / нэвтрүүлэхийн өмнөх эрсдэл

1. **«403 TOOT» дүрэм** нь бизнесийн шийдвэрээр 3-1-403 руу заана. Өөр байрны 403
   (жишээ 5-1-403) айл гүйлгээндээ зөвхөн «403 TOOT» гэж бичвэл 3-1-403-т
   бүртгэгдэнэ. Auto-apply асаахаас өмнө СӨХ-тэй дахин баталгаажуулна.
2. ICTown-ий `residents.building`-ийн бодит формат (`2-2`, `3-1`)-ыг production DB-ээс
   шалгаагүй — seed файлын ШАЛГАХ query-гээр баталгаажуулна.
3. Зарлагын SMS формат баталгаажаагүй — дэмжээгүй (review руу).
4. QPAY-ийн 15 оронтой дугаарыг банкны гүйлгээний reference гэж үзсэн. Ижил
   дугаар хоёр өөр гүйлгээнд давтагдах боломжгүй гэж таамагласан — бодит хуулгатай тулгана.
5. Нэг гүйлгээгээр хоёр сарын төлбөр (110,000₮) төлвөл автоматаар хуваахгүй —
   review руу очно (`multiple_open_invoices` / `amount_mismatch`).
6. Утас цорын ганц цэг (single point of failure). Админ дэлгэцэд «Сүүлд холбогдсон»
   харагдана; 30 минутаас дээш тасарвал «Сүүлд холбогдсон» шар болно. Push/имэйл
   сануулга хийгээгүй.
7. Android Studio-гоор build хийгээгүй тул Kotlin компайлын алдаа гарч болзошгүй.
8. Google нь 2026 оноос баталгаажаагүй хөгжүүлэгчийн APK-г certified Android дээр
   суулгахыг шат дараатай хязгаарлаж байна. Монголд хэзээ хамаарахыг шалгах;
   `adb install` нөлөөлөхгүй байх магадлалтай ч баталгаагүй.

## 8. Нөөц хувилбар (утасны дамжуулалт боломжгүй болбол)

1. **ХасБанкны байгууллагын API / хуулга** — СӨХ-ийн дансны гүйлгээний хуулгыг
   албан ёсны API-аар татах (банктай гэрээ, техникийн нөхцөлийг тодруулах шаардлагатай).
   `bank_transactions` нь эх сурвалжаас хамааралгүй тул API-ийн adapter нь SMS
   parser-ийг алгасаад `store.insertTransaction` → `matchTransaction`-ийг шууд дуудна —
   давхардал, тоот таних, төлбөр болгох дүрэм хэвээр ажиллана.
2. **Хотолын QPay нэхэмжлэх** (`app/lib/qpay.ts`) — оршин суугч апп дотроос
   төлбөл callback нь айлыг шууд мэддэг, тоот таних шаардлагагүй. Урт хугацаанд
   хамгийн найдвартай.
3. **Гараар** — интернэт банкны хуулгыг Excel-ээр импортлох (одоогийн
   «Төлбөр бүртгэх» урсгал).
